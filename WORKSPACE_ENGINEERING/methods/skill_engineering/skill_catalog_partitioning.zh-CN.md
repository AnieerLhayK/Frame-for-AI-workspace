# 稳定的 Skill Catalog 分层

当单一注册表已经成为协作瓶颈，或源码树存在若干长期稳定的所有权域时，
可以增加分类。不要仅因目录变大就增加层级：先确认类别所有权、审查或可发现性
带来的收益高于新增引用和工具维护成本。

## 选择并稳定类别

- 按用户的主要任务分类，而非实现语言、平台、团队或临时项目阶段。
- 每个 skill 只属于一个主要类别。交叉职责应放在元数据和引用中，不要重复登记。
- 保持类别词汇小而稳定。只有当多个现有或计划中的来源都需要新类别，且现有类别
  无法准确容纳时，才增加类别。
- 将所有者注册表放在源码附近，由根索引指向这些注册表。运行时消费者通过单一
  loader 聚合为兼容视图。
- Package 协议与 package 自有的 skill/tool inventory 分开。只登记可独立调用的工具，
  不要重复登记辅助脚本。

## 何时重新分类

只有当 skill 的主要用户任务实质变化、现有类别已不能真实表达维护/审查边界，或某类
已形成连贯的独立领域时，才重新分类。重命名、脚本重构、增加平台或临时项目本身，
都不足以成为移动理由。

## 安全迁移顺序

1. 记录目标分类表和精确的新旧路径。除非任务明确拥有历史记录或生成快照，否则将其排除。
2. 在旧根注册仍有效时，先增加中央 loader 和测试；保持聚合后的运行时视图稳定。
3. 从现有规范注册中生成所有者注册表，完整保留 ID、权限、执行模式、必需文件与暴露。
4. 将源码移至已批准位置，并更新注册表、投影、导入根、脚本、任务路由、文档、测试和发布契约。
5. 搜索当前源码中的旧路径，验证所有本地链接和必需文件。不要改写历史快照。
6. 将 loader 的有效 ID 与合约和迁移前快照比较；在集成前测试平台发现和公开 staging。
7. 只有在所有活动消费者都通过 loader 读取之后，才删除根级旧注册。集成后只经登记的
   publisher 发布。

## 让未来移动更容易

优先使用 manifest 相对源码路径和 skill 相对兄弟资源引用。通过已发现的 manifest 或有界
父目录查找推导 Workspace 根，避免脚本依赖固定深度的 `parents[n]`。每个 catalog 使用显式
索引，不让消费者自行扫描目录。README 和策略负责解释所有权，ID 保持稳定。增加链接与引用
测试，使未来移动能显式发现旧路径，而不是静默保留错误引用。

此方法已通过 2026 年 Workspace catalog 分层局部验证；再次应用前仍需核对当前任务路由和
平台投影合约。
